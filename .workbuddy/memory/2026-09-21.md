## ADR-018 实测收口 → **ADR-029（重大：原决策是错的）**

真实 `SslStream` server/client 握手 spike（loopback，证书 profile 严格复刻 `DeviceCertificateService`，
3 flag × 3 协议 × 重复 3 次）：

- **`EphemeralKeySet` 9/9 失败**（TLS 服务端）。服务端真实异常：
  `AuthenticationException: Authentication failed because the platform does not support ephemeral keys.`
  ← `Win32Exception: 安全包中没有可用的凭证（0x8009030E = SEC_E_NO_CREDENTIALS）`；
  客户端只能看到 `IOException: unexpected EOF` —— **必须抓服务端异常才定位得到**
- `PersistKeySet` 9/9 OK，但**磁盘留持久密钥副本**（`%APPDATA%\Microsoft\Crypto\Keys` 文件数 dispose+GC 后仍 +1）
- **`Default(0)` 9/9 OK，且密钥文件 dispose/GC 后删除** → ADR-018 想避免的"第二份持久化副本"只有它满足
- 协商：TLS1.2=`TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384`，TLS1.3=`TLS_AES_256_GCM_SHA384`，
  `Tls12|Tls13`→TLS1.3；握手后真实帧收发往返成功；pin（`GetRawCertData()`+FixedTimeEquals）全 True

**污染陷阱（务必记住）**：同一进程先 `PersistKeySet` 导入过同一私钥，再 `EphemeralKeySet` 导入 → **握手成功**。
我第一次的根因探针就是被这个污染骗了（显示 OK，与矩阵矛盾），重写成"新进程 + 顺序受控 + 重复 3 次"才定案。
→ 任何平台行为结论：**新进程、顺序受控、重复多次、两端异常都抓**。

**M3 第一步三件事（顺序不能变）**：改 `ImportFlags` → `Default`；
改掉锁住旧选择的测试 `DeviceCertificateTests.ImportFlags_UsesEphemeralKeySetOnly`；
新增真实握手集成测试。

**另测到的 .NET 10 硬事实**：证书校验回调参数是 `X509Certificate`（基类），**没有 `RawData`**，
算 pin 必须用 `GetRawCertData()`（编译器会直接报错，别绕过去）。

### 实测结论（ADR-030，重要）

`CertificateRequest.CreateSelfSigned()` 直出的证书**私钥是 ephemeral 的**，
做 Windows TLS 服务端时在 `AcquireCredentialsHandle` 失败：
`AuthenticationException: ... does not support ephemeral keys.` ← `Win32Exception 0x8009030E`。
**与 ADR-029 的 EphemeralKeySet 失败同一个错** → Schannel 拒绝的是密钥的 ephemeral 属性本身；
`DeviceCertificateService` 里"签发后导出 PFX 再 DefaultKeySet 导入"是必需环节，**不是冗余**。
测试造证书也必须复刻这条往返路径，否则与真实设备证书形态不一致。

- `TargetHost = string.Empty` 可用：不发 SNI、不做主机名校验，握手正常。
- 握手时限 400ms + 对端不握手 → 客户端在 ~400ms 被切断，异常是 `System.OperationCanceledException`。
- 判定 TLS 失败**必须抓服务端异常**：客户端永远只看到 `IOException: unexpected EOF`。

### ADR-032：我先前对 ExclusiveAddressUse 的断言是错的（实测证伪）

完整矩阵（Win11 25H2 / 26200）：
- 同端口 + 两个不同具体地址 → 开不开都**可以** bind（步骤 8 靠这条成立）
- 同地址同端口第二次 → 都**被拒**（10048）
- 别人先 bind 0.0.0.0（未开 exclusive）→ 我们再 bind 具体地址**仍成功**，开 exclusive 也发现不了
- 我们先 bind 具体地址（exclusive）→ 别人再 bind 0.0.0.0 **也成功**
- 带 SO_REUSEADDR 的后来者抢同地址同端口 → 开不开**都拒**（10013）
- 连到具体地址的连接 → 归**更具体**的 listener，不会被更宽的 socket 截走

结论：本机可观测范围内 exclusive 开不开没差别；保留 true 只为防御旧版 Windows。

### 教训（很重要）

第一版守护测试把 ExclusiveAddressUse 也开在**对照组** socket 上 →

**变异验证必须确认真的变红，否则等于没做。**

### 修掉的一个真实缺陷：验收器的空洞断言

`pin-mismatch` / `cross-subnet` 原先是「握手失败即 PASS」。对端端口没开、防火墙拦掉、
host 没启动，同样会让握手失败 → 照样 PASS，而同子网闸门和 pinning 一行都没被执行到。
已加纯 TCP 探针（不通则退 2，不判 PASS）+ `LooksLikeNothingListening` 按 `SocketError` 区分；
刻意**不**把 `ConnectionReset` 归进「没连上」（accept 后立刻关闭正是走 RST）。
**变异验证**：`192.168.1.20:45873`（无人监听）修复前 PASS/exit 0 → 修复后
`peer-port-unreachable`/exit 2。同时把 `WaitForPeerCloseAsync` 的 `catch → return true`
拆成 `eof` / `reset` / `still-open` / `unexpected-data`。

### 新发现的两个缺口（写入 HANDOFF §14.12 / §14.13）

1. **`TransportHost` 完全没有 logger**：同子网拒绝 / 准入拒绝 / TLS 失败三条路径全是静默 `return`，
   被控端对「谁被拒了、为什么」一无所知。但 pre-auth 超时发生在会话处理器**内部**，是有输出的。
   写手册前必须确认被控端到底会不会打印，不能凭「应该会记日志吧」写判定标准。并入 ADR-024 / M9。
2. **跨子网拒绝无法真机覆盖**：两机同挂 `172.100.166.x` + `192.168.1.x`，host 只听 RFC1918 绑定，
   Windows 会自动挑同子网源地址 → 做不出「源 IP 在另一子网」的样本；`New-NetRoute`/`route add`
